작업이 끝난 변경을 검증하고, 기능 단위로 쪼개서 커밋하고, push한다.
한 덩어리로 몰아 커밋하지 않는다.

## 1. 현재 상태 파악

```bash
git status --short
git diff
git diff --staged
```

변경이 없으면 여기서 끝낸다.

## 2. 검증

`pnpm verify`를 돌린다. 실패하면 커밋하지 말고 원인을 보고한다.
(push 시점에도 pre-push-verify 훅이 같은 검증을 다시 건다.)

## 3. 커밋 분할

변경을 논리 단위로 나눈다. 나누는 기준:

- 하나의 커밋은 하나의 의도만 담는다. "A를 고치면서 B도 정리했다"는
  두 커밋이다.
- 각 커밋은 그 자체로 검증을 통과해야 한다. 중간이 깨지는 분할은
  하지 않는다. (예: 의존성 설치와 그 설정은 한 커밋)
- 리팩터링과 동작 변경을 같은 커밋에 섞지 않는다.
- 자동 생성물(`docs/WORKLOG.md`, 락파일)은 그 원인이 된 커밋에 함께 넣는다.

커밋 메시지는 `.ai/rules/REVIEW.md`의 Conventional Commits를 따른다.
본문에는 무엇을 했는지가 아니라 왜 필요했는지를 쓴다 — 무엇을 했는지는
diff에 이미 있다.

## 4. 확장성 점검

push 전에 이번 변경에 대해 판단해서 보고한다:

- 새로 추가한 구조가 다음 도메인/기능에 그대로 재사용되는가,
  아니면 이번 건에만 맞춘 특수 케이스인가
- 기존 워크플로를 조이는 변경인가 (임계치, 훅, 차단 규칙 등).
  그렇다면 도입 순서를 나눠야 하는지
- 파일 추가만으로 끝나는가, 기존 코드를 건드려야 재사용되는가

## 5. push

```bash
git push
```

인자가 주어졌으면 그 원격/브랜치로 push한다.
`main`에 직접 push하는 상황이면 `.ai/rules/REVIEW.md`의 브랜치 전략상
PR을 거치는 게 원칙임을 알리고, 그래도 진행할지 확인한다.
