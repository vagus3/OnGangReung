# 009. AI 코스 생성 — LLM 연동과 키 없는 환경

날짜: 2026-09-17
상태: Accepted

## 배경 (Context)

AI 코스 탭은 사용자가 관심사와 기간을 고르고 문장을 입력하면 일정을 짜준다.

디자인 파일에는 생성 로직이 없다. `chatSend`가 1.4초 뒤에 고정 카드를 꽂는
`setTimeout` 스텁이고, 일정은 기간만의 순수 함수이며, 사용자가 입력한 문장은
`ask`에 저장만 되고 어디서도 읽히지 않는다. 즉 화면은 있고 알맹이는 없다.

제약이 둘 있다.

- 개발 환경에 `ANTHROPIC_API_KEY`가 없다. 키 없이도 화면을 확인하고 테스트를
  돌릴 수 있어야 한다 — TourAPI를 픽스처로 다룬 것과 같은 상황이다.
- 디자인의 각주가 이동 시간을 "시내버스 실시간 배차 정보" 기준이라고 적었다.
  그건 TAGO 연동이 필요한데 이번 범위가 아니다.

## 선택지 (Options)

### 가. 생성 방식

1. 규칙 기반 — 관심사·기간으로 거르고 거리로 동선 정렬
   - 장점: 비용 0, 결정적이라 테스트가 쉽다, 지연이 없다
   - 단점: 사용자가 입력한 문장을 이해하지 못한다. "아이 둘과 1박 2일, 이동은
     짧게" 같은 요청이 키워드 매칭으로 전락한다. 디자인의 챗 UI가 무의미해진다

2. LLM 생성 — 관광지 데이터를 컨텍스트로 넣고 일정을 받는다
   - 장점: 문장을 실제로 이해한다. 디자인이 그리는 경험에 맞는다
   - 단점: 비용·지연·실패 처리가 붙는다. 키가 없으면 아무것도 안 된다

### 나. 키가 없을 때

1. 오류를 띄운다
   - 단점: 개발·테스트·데모에서 탭 전체가 죽는다
2. 결정적 스텁이 응답한다
   - 단점: 스텁과 실물의 차이가 숨는다

## 결정 (Decision)

가-2(LLM 생성)와 나-2(결정적 스텁)를 선택한다.

### 구조

공공데이터 연동과 같은 모양이다 (ADR 007).

```
app/integrations/anthropic/client.py   — Protocol + 실제 클라이언트 + 스텁
app/services/ai_course.py              — 대화·일정 적재, 커밋 소유
app/api/v1/ai_courses.py               — 엔드포인트
```

서비스는 구현체가 아니라 Protocol에 의존한다. 네트워크 없이 생성 경로 전체를
테스트할 수 있어야 하기 때문이다.

### 모델과 출력

- 모델은 `claude-opus-5`
- 구조화 출력을 쓴다. `client.messages.parse(output_format=...)`에 Pydantic
  모델을 주면 검증된 객체로 돌아온다. 자유 텍스트를 파싱하면 형식이 틀렸을 때
  화면이 깨지는데, 여행 일정은 항목 수와 필드가 고정된 구조라 제약할 수 있다
- 일정 항목은 `spot_slug`를 물게 한다. 그래야 지도와 상세로 이을 수 있다.
  프롬프트에 우리 관광지 목록을 주고 그 안에서만 고르게 한다 — 존재하지 않는
  장소를 지어내면 링크가 죽는다
- 응답에서 모르는 slug는 버린다. 모델이 지침을 어길 수 있다고 전제한다

### 키가 없을 때

`StubCourseGenerator`가 관심사·기간으로 거른 결정적 일정을 돌려준다. 화면과
테스트가 돌아가고, 응답에 `generated_by` 필드를 실어 스텁인지 실물인지
클라이언트가 구분할 수 있게 한다. 숨기지 않는다.

### 이동 시간

직선거리 기준으로 어림한다. 디자인의 "시내버스 실시간 배차 정보" 문구는
지키지 못하므로 **화면 문구를 실제와 맞게 고친다.** 못 지킬 약속을 화면에
두지 않는다.

### 대화 보관

로그인 상태면 서버에, 아니면 브라우저에 둔다 (ADR 008과 같은 원칙). 디자인의
`selectHistory`는 기록에서 가짜 대화를 재구성하는데, 그러면 사용자가 받았던
일정이 사라진다. 실제 대화를 저장한다.

## 결과 (Consequences)

- 긍정적:
  - 키 없이도 탭이 동작하고 테스트가 돈다
  - 구조화 출력이라 화면이 형식 오류로 깨지지 않는다
  - 일정이 실제 관광지를 가리켜 지도·상세로 이어진다
- 부정적:
  - 스텁과 실물의 품질 차이가 개발 중에는 드러나지 않는다.
    `generated_by`로 최소한 구분은 된다
  - LLM 호출 비용과 지연이 생긴다. 생성은 초 단위이므로 화면에 진행 표시가 필요하다
  - 프롬프트가 관광지 목록을 통째로 싣는다. 관광지가 수백 건이 되면
    권역·관심사로 먼저 좁혀야 한다
- 향후 고려사항:
  - 이동 시간을 제대로 하려면 TAGO 또는 경로 API가 필요하다
  - 같은 질문이 반복되면 프롬프트 캐싱으로 관광지 목록을 재사용할 수 있다
  - 생성 품질을 재려면 eval 세트가 필요하다. 지금은 없다
