# 007. 공공데이터 연동 계층 도입 — `app/integrations/` 과 동기화 전략

날짜: 2026-09-14
상태: Accepted

## 배경 (Context)

강릉 관광 앱은 공공데이터포털(data.go.kr)의 여러 기관 API에 의존한다. 기능별로
필요한 API는 `docs/api/public-data-apis.md`에 정리했고, 요약하면 한국관광공사
TourAPI(관광지·축제·무장애·다국어), 기상청 단기예보(날씨·파고·수온),
국토교통부 TAGO(버스), 전국주차장정보 등이다.

이 연동은 기존 아키텍처에 들어갈 자리가 없다.

`.ai/rules/ARCHITECTURE.md` §5가 허용하는 백엔드 의존 방향은
`api → services, schemas, db` / `services → models, schemas, core` /
`db → models, core`뿐이다. 외부로 HTTP를 나가는 구성요소가 이 그래프에 없다.
`.ai/DATABASE.md`에도 리포지토리 패턴 규칙이 없어 (질의는 서비스에 직접 들어간다)
거기에 얹을 자리도 없다.

또 하나의 문제는 데이터 소유권이다. 디자인의 관광지 레코드를 TourAPI 필드와
대조하면 두 종류가 섞여 있다.

- 외부 사실 (한국관광공사 소유, 주기적으로 변함): 이름, 주소, 전화, 좌표,
  운영시간, 요금, 대표사진
- 편집 저작물 (우리 소유): 소개 문구("하늘, 바다, 호수, 술잔, 그대 눈동자"),
  스티커("다섯 개의 달"), 카드 레이아웃 지시(`span`), 권역 분류, 큐레이션 태그,
  자체 카테고리

수명주기가 다른 이 둘을 어디에 어떻게 둘지 정해야 한다.

## 선택지 (Options)

### 가. 호출 방식

1. 런타임 프록시 — 요청마다 백엔드가 공공 API를 호출하고 캐시
   - 장점: 항상 최신. 적재 로직이 없다
   - 단점: 외부 장애가 그대로 사용자에게 전파된다. 개발계정 트래픽이 1,000건으로
     제한돼 있어 실사용에서 즉시 고갈된다. 우리 고유 필드를 붙일 자리가 없어
     별도 테이블을 조인해야 하는데, 그러면 아래 다-2와 같은 구조가 되면서
     캐시 무효화 문제만 추가된다

2. 배치 동기화 — 주기적으로 우리 DB에 적재, 앱은 우리 DB만 조회
   - 장점: 응답이 빠르고 외부 장애·쿼터와 격리된다. 우리 고유 필드를 같은 곳에
     둘 수 있다. 오프라인 모드(디자인 요구사항)의 전제가 된다
   - 단점: 신선도가 동기화 주기만큼 떨어진다. 적재 로직과 그 테스트가 필요하다

3. 하이브리드 — 정적 데이터는 동기화, 실시간성 데이터는 프록시
   - 장점: 각 데이터 성격에 맞다
   - 단점: 경로가 둘이라 코드가 늘어난다

### 나. 클라이언트 구조

1. API별 독립 클라이언트
   - 장점: 각자 단순하다
   - 단점: data.go.kr API는 인증(`serviceKey`), 페이징(`numOfRows`/`pageNo`),
     응답 형식(`_type=json`), 봉투(`response.header.resultCode` /
     `response.body.items.item[]` / `totalCount`), 오류 코드 체계가 **전부 동일**하다.
     API를 추가할 때마다 같은 코드를 복사하게 된다

2. 공통 베이스 + API별 얇은 타입 레이어
   - 장점: 공유 규약을 한 곳에서 처리한다. 새 API 추가가 스키마 정의와 파라미터
     매핑만으로 끝난다
   - 단점: 추상화가 하나 늘어난다

### 다. 저장 구조

1. 단일 테이블 + 필드별 소유권 — `source_*` 컬럼과 편집 컬럼을 한 행에 두고
   동기화는 `source_*`만 갱신
   - 장점: 조인이 없다
   - 단점: 소유권이 코드 컨벤션으로만 존재한다. 실수로 편집 필드를 덮는 것을
     스키마가 막지 못한다. TourAPI에 없는 장소는 `source_*`가 전부 NULL인 행이
     되고, 큐레이션되지 않은 외부 콘텐츠는 표현할 자리가 없다

2. 외부 미러 테이블 + 편집 엔티티 테이블 분리
   - 장점: 동기화 잡이 편집 테이블에 접근하지 않으므로 편집 데이터 유실이
     구조적으로 불가능하다. 외부에 없는 장소와 큐레이션되지 않은 외부 콘텐츠를
     양쪽 다 표현할 수 있다. 원본이 보존돼 매핑 규칙을 바꿔도 재동기화가 필요 없다
   - 단점: 테이블이 늘고 조회에 조인이 하나 붙는다

3. 3계층 (원본 JSON 스냅샷 + 정규화 + 오버레이)
   - 장점: 이력 추적과 재처리에 가장 강하다
   - 단점: 지금 필요하지 않은 유연성이다

## 결정 (Decision)

가-2(배치 동기화), 나-2(공통 베이스), 다-2(테이블 분리)를 선택한다.

### 배치 구조

| 경로                                    | 역할                                                     | 의존 방향                |
| --------------------------------------- | -------------------------------------------------------- | ------------------------ |
| `app/integrations/publicdata/client.py` | data.go.kr 공통 베이스 — 인증·페이징·봉투 파싱·오류 변환 | `core`만                 |
| `app/integrations/tourapi/`             | TourAPI 파라미터·응답 스키마                             | 공통 베이스              |
| `app/integrations/<기관>/`              | 이후 추가되는 기관별 레이어                              | 공통 베이스              |
| `app/services/<도메인>_sync.py`         | 적재·upsert 오케스트레이션. 커밋 소유                    | `integrations`, `models` |
| `apps/api/scripts/sync_*.py`            | CLI 진입점                                               | `services`               |

`app/integrations/`는 `services` / `api` / `models`를 import하지 않는다. 외부 계약을
Pydantic 모델로 번역하는 것까지가 책임이고, 우리 도메인 모델을 아는 것은 서비스의
책임이다. 이렇게 두면 외부 API가 바뀌어도 파급이 `integrations` 안에서 멈춘다.

`.ai/rules/ARCHITECTURE.md` §5의 허용 방향에 다음 한 줄을 추가하는 것과 같다:

```
services → integrations
integrations → core
```

### 동기화 시맨틱

- 외부 식별자(TourAPI `contentid` 등)를 기본키로 삼아 개별 upsert
- 외부의 수정 시각(`modifiedtime`)이 우리가 기록한 값보다 새로울 때만 갱신
- 외부에서 사라진 레코드는 **삭제하지 않고** `is_active=False`로 내린다.
  편집 엔티티가 참조하고 있을 수 있기 때문이다. FK는 안전망으로 `ondelete=SET NULL`
- Postgres 전용 `on_conflict_do_update`는 쓰지 않는다. 테스트가 인메모리 SQLite로
  돌기 때문에(`.ai/DATABASE.md`) 이식 가능한 방식(기존 id 조회 후 insert/update 분기)을
  쓴다

### 트리거

슬라이스 1에서는 CLI만 제공한다(`uv run python -m scripts.sync_tourapi`).
HTTP 트리거 엔드포인트는 만들지 않는다 — 장시간 외부 호출을 요청-응답 주기에
띄우려면 인증과 백그라운드 작업 기반이 필요한데 둘 다 아직 없다. 운영에서는
CronJob으로 이 CLI를 호출한다(`.ai/rules/INFRA.md`의 Kubernetes 구성과 맞는다).

### 테스트

클라이언트를 `Protocol`로 정의하고 가짜 구현을 주입한다. httpx transport mock보다
경계가 명확하고, 네트워크 없이 적재 로직 전체를 검증할 수 있다. 응답 픽스처는
`apps/api/tests/fixtures/<기관>/*.json`에 둔다.

## 결과 (Consequences)

- 긍정적:
  - 편집 데이터 유실이 스키마 수준에서 불가능해진다
  - 새 공공 API 추가가 스키마 정의 + 파라미터 매핑으로 끝난다
  - 외부 장애·쿼터가 사용자에게 전파되지 않는다. 오프라인 모드의 전제가 선다
  - API 키 없이도 전체 적재 경로를 테스트할 수 있다
- 부정적:
  - 데이터 신선도가 동기화 주기에 묶인다. 실시간성이 필요한 데이터(버스 도착 등)는
    이 구조에 맞지 않아 별도 판단이 필요하다
  - 조회에 조인이 하나 늘고, 동기화 잡의 운영(스케줄·실패 알림)이 필요해진다
  - `app/integrations/`가 ARCHITECTURE.md §5 그래프에 없던 노드다. 문서를 함께
    갱신하지 않으면 리뷰에서 위반으로 읽힌다
- 향후 고려사항:
  - 버스 도착정보처럼 초 단위 신선도가 필요한 API는 동기화 대상이 아니다.
    그 시점에 런타임 프록시 경로를 예외로 추가하고 이 ADR을 잇는 ADR을 쓴다
  - 개발계정 트래픽 1,000건 제한이 있다. 전체 적재를 반복 실행하면 즉시 고갈되므로
    운영계정 전환 전까지 `--dry-run`과 페이지 제한을 기본값으로 둔다
  - 기상청 격자 좌표(`nx`/`ny`)는 하드코딩하지 않고 위경도 → 격자 변환식으로
    계산한다. 값이 코드에 박히면 지역 확장(속초·동해) 때 막힌다
